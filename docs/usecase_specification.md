# Uni-Steps ユースケース（アプリケーションビジネスロジック層）仕様書

本ドキュメントでは，Uni-Stepsプロジェクトのバックエンドにおいて，アプリケーションの具体的な業務フロー（ビジネスロジック）を担う「ユースケース（アプリケーションビジネスロジック層）」の各ファイルについて，役割，他レイヤー（ドメイン層，インフラ層，インターフェース層）との具体的なデータ連携手順を，詳細に解説する．

## 1. 用語解説

ユースケース層のコードを読む前に，設計上重要となる用語を整理しておく．

| 用語                           | 読み方・別名                       | 初学者向けの簡単な意味                                                                                                                                                                                |
| :----------------------------- | :--------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ユースケース**         | Usecase / アプリケーションサービス | **「システムの料理人（業務手続きの実行者）」**．「タスクを登録してリマインドを設定する」「Classroomから同期して差分を保存する」など，具体的な業務フローをコントロールするロジック．             |
| **リポジトリ**           | Repository / 永続化層              | **「データ保管庫（データベース）の出入り口」**．SQLなどの技術的な知識はリポジトリの奥に隠されており，ユースケースからは単に `Save` や `FindByID` といった関数を通じてデータを出し入れする． |
| **ドメインオブジェクト** | Domain Object / エンティティ       | **「ビジネスで扱うモノの設計図」**．`User` や `Task` などのデータ構造と，それに直接結びつく最小限のルール（バリデーションや初期値設定など）を定義したオブジェクト．                         |
| **スケジューラー**       | Scheduler                          | **「タイマー予約システム」**．「指定の日時になったらリマインド通知を送る」「起床猶予が過ぎたらSOSアラートを発信する」といった未来のタスクを予約・実行する仕組み．                               |
| **アソシエーション**     | Association                        | **「データ同士の紐付け」**．タスクに対して誰が担当者か（TaskUserProgress），ユーザーがどのグループに所属しているか（UserGroup）といったデータ間の関連性．                                       |

## 2. ユースケース層の役割と処理フローの基本

ユースケース層（[backend/usecase](file:///home/yuma25/github/Uni-Steps/backend/usecase) パッケージ）は，システムの「中枢」である．

### 飲食店での役割例え：

* **ハンドラー（受付・ウェイター）**: お客様から「タスク登録」の注文を受け，データをチェックして調理場（ユースケース）に流す．
* **ユースケース（料理人）**: **本仕様書が担当する部分**．注文を受け，レシピ通りに料理を作る．「DB（冷蔵庫）からユーザー情報を探す」「期限を確認する」「タスクを保存する」「通知のタイマー予約をかける」といった一連の手順を順番通りに実行する．
* **リポジトリ・サービス（食材置き場・外部ツール）**: 冷蔵庫（データベース）から食材を取り出したり，LINE BotやGemini AI（自動調理家電）を使ってメッセージを作成したりする．

ユースケースは，ハンドラーとインフラ（データベースやAI，外部API）の間に立ち，システム固有の業務ルールをすべて実行する役割を持つ．

## 3. 各ユースケースファイルの詳細解説

### ① [group_uc.go](file:///home/yuma25/github/Uni-Steps/backend/usecase/group_uc.go)

* **やること**: 部屋（グループ）の新規作成，招待コードによるメンバー参加，所属グループ一覧の取得，設定変更（リマインドやAIの性格，LINE連携など），メンバーの退出，オーナー権限の譲渡，部屋の削除処理を行う．
* **なぜ必要か？**: ユーザーがタスク管理や起床見守りを行うための「箱（グループ）」を安全に作成・管理し，その中での設定変更や権限管理を制御するためである．
* **主要なメソッド**:
  * `CreateGroup`: 新しい部屋を作成し，作成したユーザーをオーナー（管理者）かつメンバーとして登録する．
  * `JoinGroupByInviteCode`: 招待コードを検証し，ユーザーをその部屋に所属させる．
  * `UpdateSettings`: 部屋の名前，リマインド間隔，AIキャラクター，LINE連携設定，サマリ送信時間を更新する（オーナーのみ実行可能）．
  * `LeaveGroup`: グループからメンバーを外す．（※オーナーが退出する場合は，事前に別の人へのオーナー権限譲渡を強制するビジネスルールを実装している）．
* **依存関係（注入される道具）**:
  * `groupRepo`: `domain.GroupRepository`（グループデータの保存・検索）
  * `userRepo`: `domain.UserRepository`（オーナーや参加ユーザーの実在確認）
  * `logRepo`: `domain.NotificationLogRepository`（グループ内の過去の通知履歴の取得）
* **具体的なデータ連携手順（CreateGroupの例）**:
  1. [User](file:///home/yuma25/github/Uni-Steps/backend/domain/user.go#L7) が実在するかを `userRepo.FindByID` で確認する．
  2. UUIDを用いた新しいグループIDと，簡易的な招待コード（8文字のランダム文字列）を生成し，デフォルト設定値を適用した [Group](file:///home/yuma25/github/Uni-Steps/backend/domain/group.go#L7) 構造体をメモリ上に作成する．
  3. `groupRepo.Save` を呼び出し，データベースにグループの基本情報を永続化する．
  4. `groupRepo.AddUserToGroup` を呼び出し，中間テーブルに「グループID」と「オーナーのユーザーID」のレコードを登録することで，所属関係を確立する．

### ② [summary_uc.go](file:///home/yuma25/github/Uni-Steps/backend/usecase/summary_uc.go)

* **やること**: 朝・夕の設定時刻に，グループメンバー全員の「その日の未完了課題」を集計し，Gemini AIに要約メッセージを作らせ，グループ全体のLINEおよび各自のスマホへサマリ通知を一括配信する．
* **なぜ必要か？**: メンバー全員が「誰がどの課題を抱えているか」「明日までにどれを終わらせるべきか」を毎日自動で共有し，チーム全体のタスク漏れを防ぐためである．
* **主要なメソッド**:
  * `SendAllSummaries`: 全グループの設定時刻を毎分チェックし，送信時間に達したグループに対してサマリ配信をトリガーする．
  * `ProcessSingleGroupSummary`: 指定されたグループに対してサマリを生成し，LINE/WebPushでの送信と履歴への保存を実行する．
* **依存関係（注入される道具）**:
  * `groupRepo`: `domain.GroupRepository`（全グループの取得と設定時刻の確認）
  * `taskRepo`: `domain.TaskRepository`（グループ内の全タスクと進捗状況の取得）
  * `aiService`: `domain.AIService`（集計テキストをGemini AIに渡して要約文を生成）
  * `notifService`: `domain.NotificationService`（LINEおよびWebPushへのメッセージ送信）
  * `logRepo`: `domain.NotificationLogRepository`（送信した通知内容の履歴ログ保存）
* **具体的なデータ連携手順**:
  1. `taskRepo.FindByGroupID` で部屋のタスクを全件ロードする．
  2. 現在時刻基準で，「朝刊（今日期限の未完了課題）」または「夕刊（明日期限の未完了課題）」に該当するものをメンバーごとに分類・テキスト集計する．
  3. 集計結果と部屋のAI設定（性格）を `aiService.GenerateGroupSummaryMessage` に引き渡し，AIによる応援・要約メッセージを生成させる．
  4. 生成された文章を `notifService.SendGroupMessage` でLINEグループに送り，さらに `notifService.SendDirectMessage` でメンバー各自のスマホブラウザへプッシュ送信する．
  5. 送信したログを `logRepo.Save` でデータベースに保存し，後から履歴を確認できるようにする．

### ③ [sync_uc.go](file:///home/yuma25/github/Uni-Steps/backend/usecase/sync_uc.go)

* **やること**: Google Classroomから課題データを自動取得し，Uni-Steps内のデータベース情報と同期（新規作成・更新・完了状態の同期）させ，必要に応じて未来のリマインド通知を自動予約する．
* **なぜ必要か？**: 大学や学校で使われているLMS（Google Classroomなど）に登録された課題を，手入力することなく自動で取り込み，提出期限の追跡を開始するためである．
* **主要なメソッド**:
  * `SyncTasks`: 指定ユーザーの認証情報を用いて特定のグループに紐づくClassroom課題を同期する．
  * `SyncAllGroups`: 6時間おきの自動同期処理において，システム内の全グループの全ユーザーに対して一括同期を実行する．
* **依存関係（注入される道具）**:
  * `taskRepo`: `domain.TaskRepository`（同期したタスクのDB保存・更新）
  * `groupRepo`: `domain.GroupRepository`（グループ情報のロードと同期完了日時のアップデート）
  * `lmsService`: `domain.LMSService`（Google Classroom APIから課題一覧をフェッチする外部通信インターフェース）
  * `scheduler`: `domain.SchedulerService`（同期によって新規作成・更新されたタスクのリマインドタイマー予約）
* **具体的なデータ連携手順**:
  1. `lmsService.FetchTasks` を呼び出し，Google Classroom側から最新の課題一覧（期限やタイトルなど）を取得する（外部APIとの通信）．
  2. `taskRepo.FindByGroupID` を呼び出して，すでにUni-Steps側に登録されているタスクを一括ロードし，メモリ上でマップ化する（N+1クエリ問題の防止）．
  3. LMS側の課題ID（`ExternalID`）をキーにローカルデータと比較する．
     * **既存データがない場合**: 新規タスクとしてUUIDを発行し，メンバー全員分の進捗レコード（`TaskUserProgress`）を未完了状態で紐付ける．
     * **既存データがある場合**: 変更があればタイトル等を更新する．（※ユーザーが手動で期限を調整した形跡がある場合は，LMS側の期限で上書きしないようにするロジックを実装している）．
  4. `taskRepo.Save` でデータベースに結果を保存する．
  5. 課題期限が未来であり，かつ未完了メンバーが残っている場合は，`scheduler.ScheduleTaskRemind` を呼び出して，部屋の設定時間（例：1日前など）に合わせたリマインド通知を予約する．

### ④ [task_uc.go](file:///home/yuma25/github/Uni-Steps/backend/usecase/task_uc.go)

* **やること**: 手動での課題登録，一覧取得，課題の編集（タイトル・期限・担当者），課題の削除，および各ユーザーによる完了・未完了状態のトグル切り替えと，それに伴うリマインド通知予約の制御を行う．
* **なぜ必要か？**: Classroomから取得した課題だけでなく，グループ内の独自の予定や手動課題の追加・編集を管理し，完了状態に応じてリマインドのオン/オフを動的に切り替えるためである．
* **主要なメソッド**:
  * `RegisterManualTask`: 手動の課題を作成し，リマインドを予約する．
  * `UpdateTask`: 課題の情報を更新する．（※期限を過ぎた手動課題の編集禁止，および作成者・オーナー以外によるタイトル変更の禁止などの権限ルールを適用する）．また，担当者が0人になったタスクは自動削除する．
  * `ToggleUserCompletion`: 指定したユーザーの課題完了フラグを反転させる．全員が完了した場合はリマインドを自動キャンセルし，未完了に戻った場合は再予約する．
* **依存関係（注入される道具）**:
  * `taskRepo`: `domain.TaskRepository`
  * `groupRepo`: `domain.GroupRepository`
  * `aiService`: `domain.AIService`
  * `scheduler`: `domain.SchedulerService`
* **具体的なデータ連携手順（ToggleUserCompletionの例）**:
  1. `taskRepo.FindByID` で現在のタスク情報をロードする．
  2. タスクの `UserProgress` 配列から該当ユーザーを探し，`IsCompleted` を反転（`true` ➔ `false` またはその逆）させ，更新日時をセットする．
  3. タスク内のすべての `UserProgress` を精査し，全員が完了状態になったかをチェックする．
     * **全員完了した場合**: `scheduler.CancelTaskReminds` を呼び出し，設定されていたリマインドタイマーをすべて破棄する（無駄な通知を防ぐ）．
     * **未完了に戻った場合**: 期限が未来であれば，`scheduler.ScheduleTaskRemind` を呼び出して，再度リマインド通知をスケジュール予約する．
  4. `taskRepo.Save` を呼び出し，DBに進捗状態を保存する．

### ⑤ [wakeup_uc.go](file:///home/yuma25/github/Uni-Steps/backend/usecase/wakeup_uc.go)

* **やること**: 起床予定時刻と猶予時間を指定した「起床見守り」のセット（予約），本人の起床報告による見守りの完了，見守りのキャンセル，およびアクティブな見守り情報の取得を行う．
* **なぜ必要か？**: 設定時間になっても起きない場合にグループメンバーへSOS通知を送る機能のコアロジックであり，タイマーの作成・破棄とDBの記録を安全に同期させるためである．
* **主要なメソッド**:
  * `RequestWakeup`: 新しい起床見守りをDBに記録し，スケジューラーに「起床予定時刻 ＋ 猶予時間（grace_minutes）」のタイミングでSOS通知を送信するタイマーを予約する．
  * `ConfirmWakeup`: ユーザーが「起きました！」ボタンを押した際に，見守り状態を「完了」にし，予約されていたSOS通知タイマーを解除（キャンセル）する．
  * `CancelWakeup`: 進行中の見守りレコードを削除し，SOS送信予約もキャンセルする．
* **依存関係（注入される道具）**:
  * `wakeupRepo`: `domain.WakeupRepository`（起床見守りレコードの保存・検索・削除）
  * `scheduler`: `domain.SchedulerService`（SOS自動発信タイマーの登録と解除）
* **具体的なデータ連携手順（ConfirmWakeupの例）**:
  1. `wakeupRepo.FindActiveByUser` を呼び出し，該当ユーザーがセットした現在進行中（未確認状態）の起床見守りレコードを取得する．
  2. 各レコードのステータス（`Status`）を `domain.WakeupStatusConfirmed`（起床確認済み）に更新し，`wakeupRepo.Save` で保存する．
  3. `scheduler.CancelWakeupSOS` を呼び出し，スケジューラーに登録されていた「SOS発信予約」をキャンセルしてタイマーを破棄する．これにより，SOSが仲間に誤送信されるのを防ぐ．

## 4. なぜ直接データベース（SQL）を操作しないのか？

ユースケース層では，SQL文（`gormDB.Where().Update()` など）を直接記述しない．

これはクリーンアーキテクチャの**「フレームワークとドライバーの隔離」**というルールに基づく．

### 直接DBを触らない設計のメリット：

1. **データベース技術の隠蔽**:
   ユースケース層は `taskRepo.Save(ctx, task)` と呼び出すだけであり，裏で動いているデータベースが PostgreSQL なのか MySQL なのか，あるいはモック用のオンメモリDBなのかを知る必要がない．
2. **テストの簡素化**:
   データベースに接続しなくても，リポジトリの「フリ（Mock）」をするオブジェクトをテスト時に渡してあげるだけで，ビジネスロジックの判定が正しいか（例：期限切れのタスクの編集がエラーになるかなど）を100%検証できる．
