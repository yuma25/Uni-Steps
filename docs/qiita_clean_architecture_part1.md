# 【第1回】Uni-Stepsで学ぶクリーンアーキテクチャ：全体概要と基本思想

大学生やチーム向けのタスク・生活管理アプリ「Uni-Steps」の構造を題材に，バックエンド（Go）からフロントエンド（TypeScript/React）にわたるクリーンアーキテクチャの実践方法を解説する連載の第1回である．

本記事では，「なぜクリーンアーキテクチャを採用するのか」という根本的な思想と，本アプリ **Uni-Steps** の全体的な設計・ディレクトリ構造について，初心者にも分かりやすく解説する．

---

## 1. なぜクリーンアーキテクチャが必要なのか？

システム開発において，最も避けるべきなのは**「密結合（スパゲッティコード）」**である．

例えば，以下のようなコードが挙げられる．
*   APIのコントローラーの中に，直接SQLクエリが書かれている．
*   データベースのテーブル構造を変えたら，画面のHTMLや表示ロジックまで壊れてしまった．
*   テストを書こうとしたが，実際にデータベースや外部APIが動いていないとテストが実行できない．

これらはすべて，**「ビジネスロジック（システムが解決したい本来の目的）」**と**「技術的詳細（データベース，Webフレームワーク，外部サービスなど）」**が混ざり合ってしまっていることが原因である．

**クリーンアーキテクチャ（Clean Architecture）**は，これらを同心円状のレイヤーに分離し，**「依存の方向を常に内側（ビジネスロジック）に向ける」**というルールを徹底することで，これらの問題を解決する．

```
   ┌───────────────────────────────────────────────┐
   │ 外部世界 (Web, Database, UI, Devices)          │
   │      ┌─────────────────────────────────┐      │
   │      │ インターフェース (Controllers, Gateways) │      │
   │      │      ┌───────────────────┐      │      │
   │      │      │ ユースケース (Use Cases)  │      │      │
   │      │      │      ┌─────┐      │      │      │
   │      │      │      │Domain│     │      │      │
   │      │      │      └─────┘      │      │      │
   │      │      └───────────────────┘      │      │
   │      └─────────────────────────────────┘      │
   └───────────────────────────────────────────────┘
                     依存の方向 ───> 内側へ
```

### クリーンアーキテクチャの黄金律
*   **内側の円は，外側の円について何も知らない**：
    ビジネスロジック（内側）は，データベースに何を使っているか（PostgreSQLなのかMySQLなのか），Webフレームワークに何を使っているか（EchoなのかGinなのか）を一切知らないし，知る必要もない．
*   **外側は詳細，内側は本質**：
    データベースやWebフレームワークは，ビジネスロジックという「本質」を動かすための「詳細（プラグイン）」に過ぎない．

### コラム：「制御の流れ」と「依存の方向」の決定的な違い

クリーンアーキテクチャの同心円図を見ると，「Domain（ドメイン）が中央にあり，そこから外側に向けてデータが広がっていくだけなのではないか」と錯覚しやすい．しかし，実際はそうではない．

クリーンアーキテクチャを正しく理解するためには，**「制御の流れ（処理の順序）」**と**「依存の方向（コードの参照関係）」**という2つの異なる軸を区別する必要がある．

#### ① 制御の流れ（処理が流れるルート）
実際のプログラムの動き（データの流れ）は，ユーザーのブラウザ操作から始まり，以下のように同心円を外から内へ，そして再び外へと通り抜けていく．

```
【 制御の流れ (データが流れる順序) 】

[ブラウザ(最外周)] ➔ [Handler(外周)] ➔ [UseCase(内周)] ➔ [Domain(中心)] ➔ [DB(最外周)]
```

つまり，プログラムの実行順序は「外 ➔ 内 ➔ 外」というルートを通る．

#### ② 依存の方向（ソースコードの参照関係）
一方で，ソースコード上の依存関係（どのファイルがどのファイルを `import` しているか）のルールは，常に **「外側から内側（中心）へ」の一方向のみ**に制限される．

*   **Handler (外)** は，**UseCase (内)** や **Domain (中心)** を知っている（`import` する）．
*   **UseCase (内)** は，**Domain (中心)** だけを知っている．
*   **Domain (中心)** は，外側のレイヤーを一切知らない（インポートしない）．

「処理は内側（UseCase）から外側（DB）へ向かうのに，コードの依存関係を外から内へ制限する（DBを知らない状態にする）のは矛盾しているのではないか？」と思うかもしれない．
この矛盾を解決し，依存関係をひっくり返す魔法が，第2回で解説する **「依存関係逆転の原則（DIP）」** である．

## 2. Uni-Stepsのシステム構成と技術スタック

本連載の題材となる「Uni-Steps」は，以下のモダンな技術スタックで構築されている．

*   **バックエンド (Go)**:
    *   **Webフレームワーク**: Echo (高速かつシンプルなGoのWebフレームワーク)
    *   **ORM (DB操作)**: GORM (Go用の高機能なORM)
    *   **データベース**: PostgreSQL
*   **フロントエンド (TypeScript / React)**:
    *   **ビルドツール**: Vite
    *   **状態管理・UI**: React (Hooksを活用)

この構成において，バックエンドだけでなくフロントエンドにも「関心の分離（クリーンアーキテクチャの思想）」を適用している．

## 3. バックエンドのフォルダ構成と役割分担

バックエンドのソースコードは，クリーンアーキテクチャの思想に基づいて綺麗に4つのレイヤーに分割されている．
現実世界の「工事現場」や「お店」に例えると，それぞれの役割が理解しやすい．

```
Uni-Steps (Backend)
 ├── domain/          # 【設計図・ルール】ビジネスのルールや型定義
 ├── usecase/         # 【現場監督】ビジネスロジックの実行手順
 ├── interfaces/      # 【受付窓口】HTTPリクエストの受付とレスポンス (Handler)
 └── infrastructure/  # 【道具・機材】DBアクセスや外部サービス (LINE, Gemini) の具象実装
```

### ① Domain（ドメイン）レイヤー：設計図
*   **役割**: システムが扱うオブジェクト（タスク，ユーザー，グループなど）のデータ構造と，ビジネスルール（インターフェース）を定義する．
*   **特徴**: 他のどのレイヤーにも依存しない，最も純粋な領域である．ここにはSQLの実行コードや，外部APIの呼び出しコードは一切記述しない．
*   **ファイル例**:
    *   `domain/task.go`：タスクの構造体定義
    *   `domain/repository.go`：データベースに対する「約束事（インターフェース）」の定義

### ② UseCase（ユースケース）レイヤー：現場監督
*   **役割**: ユーザーのアクション（「タスクを登録する」「進捗を変更する」など）に応じて，どのような手順で処理を行うかをコントロールする．
*   **特徴**: ドメインモデルとドメインリポジトリのインターフェースだけを使って処理を組み立てる．具体的なDB操作コードは持たず，インターフェースを通じて指示を出す役割を担う．
*   **ファイル例**:
    *   `usecase/task_uc.go`：タスク登録や更新のビジネスロジック

### ③ Interfaces（インターフェース）レイヤー：受付窓口
*   **役割**: 外部（フロントエンド）からのHTTPリクエストを受け取り，適切なUseCaseに処理を依頼し，結果をJSONなどの形式で送り返す．
*   **特徴**: Webフレームワーク（Echo）に依存するコードはここに集約される．
*   **ファイル例**:
    *   `interfaces/handler/task_handler.go`：Echoを用いたHTTPハンドラーの実装

### ④ Infrastructure（インフラストラクチャ）レイヤー：道具・機材
*   **役割**: データベースへのアクセス，AI（Gemini API）の呼び出し，LINE通知の送信など，具体的な「技術的詳細」を実装する．
*   **特徴**: Domainレイヤーで定義されたインターフェースを実際に満たす（実装する）レイヤーである．
*   **ファイル例**:
    *   `infrastructure/db/task_repository.go`：GORMを使ってPostgreSQLにデータを保存する具象クラス

## 4. フロントエンドのフォルダ構成と役割分担

「クリーンアーキテクチャはバックエンドだけのもの」と思われがちであるが，フロントエンドでも同じ思想を適用することで，UIコンポーネントが肥大化するのを防ぐことができる．

```
Uni-Steps (Frontend/src)
 ├── types/           # 【設計図】データの型定義 (Domain)
 ├── hooks/           # 【現場監督】状態管理とビジネスロジック (UseCase)
 ├── pages/           # 【表示板・操作パネル】画面のレイアウト (Presenter)
 └── api/             # 【通信用の道具】外部APIとの通信 (Infrastructure)
```

| クリーンアーキテクチャの役割 | フロントエンドでの実装 | 役割 |
| :--- | :--- | :--- |
| **Domain (実体)** | `types/` (TypeScriptの型定義) | アプリケーションで扱うデータ構造の定義 |
| **UseCase (ロジック)** | `hooks/` (カスタムフック) | 画面の状態管理 (useState) やAPI呼び出しの実行制御 |
| **Presenter (表現)** | `pages/`, `components/` | JSXを用いたUIのレンダリングと，ユーザー操作の検知 |
| **Infrastructure (インフラ)**| `api/` (Axios/fetchによる通信) | サーバーAPIとのHTTP通信の具象実装 |

このように役割を分けることで，例えば「UIのデザインを変更したい」ときは `pages/` や `components/` だけを修正すればよく，「APIの通信先やエラーハンドリングを変えたい」ときは `api/` や `hooks/` を修正するだけで済むようになる．

## 5. まとめと次回予告

第1回では，クリーンアーキテクチャの基本思想と，Uni-Stepsにおけるフォルダ構成のマッピングを整理した．

*   **依存関係は常に「外側から内側へ」**．
*   **ビジネスロジック（Domain, UseCase）は技術（DB, Framework）を知らない**．
*   **フロントエンドでも同様の関心の分離が有効である**．

次回は，具体的なコードの解説に入る．
**「第2回：バックエンド編①：Domain と UseCase 〜データベースを一切知らない純粋なビジネス領域〜」**と題して，Goでの具体的なインターフェース定義とユースケースの組み立て方を解説する．
